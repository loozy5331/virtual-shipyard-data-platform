# ADR-003 MVP 입구는 파일 착륙 구역

- 상태: 확정
- 날짜: 2026-11-10

## 맥락

원천은 이벤트를 파일로도, Kafka로도 보낸다. 처음 계획은 입구를 처음부터 Kafka로 두었지만, MVP 없이 최종 형태부터 까는 것이라 과했다. Kafka를 들인 까닭도 겪은 문제로 설명할 수 없었다.
원천 ADR-007은 착륙 구역부터 플랫폼의 것이라고 정했고, 파일 형식은 원천 ADR-005(방출)와 ADR-006(재발행)이 정했다.

## 결정

1. **Phase 1~3의 입구는 파일 착륙 구역 `data/landing/`이다**
   - 원천 방출기가 이곳에 쓴다: `uv run python -m emitter --out-dir ../virtual-shipyard-data-platform/data/landing`.
   - 파일은 `dt=<YYYY-MM-DD>/part-*.jsonl`, 한 줄이 봉투 JSON 하나다. `part-0.jsonl`은 방출분(`dt` = 도착 날짜), `part-replay-<처리 시각>.jsonl`은 재발행분(`dt` = 처리 날짜, Phase 2)이다.
   - bronze는 `dt`의 `part-*.jsonl`을 모두 읽는다. `part-0.jsonl`만 읽으면 재발행분이 조용히 빠진다.
   - 착륙 구역의 보존·정리와 어디까지 읽었는지는 플랫폼이 맡는다.
2. **같은 `dt`를 다시 읽어도 결과가 같다**: bronze는 `dt`마다 덮어쓴다. 파일 입구에는 오프셋이 없으니, 수집의 신뢰성은 "같은 `dt`를 다시 돌리면 같은 결과"가 맡는다.
3. **Kafka는 실시간 요구가 생길 때 들인다(Phase 4)**
   - 하루 단위 파일 배치로는 지금 설비가 섰는지 다음 날에야 안다. 이 문제가 스트림을 부르고, 스트림이 Kafka를 부른다.
   - 그때 입구가 둘이 되니 배치 입구도 Kafka로 옮겨 하나로 합친다. 토픽·키·파티션·보존 기간은 그때 ADR-007로 정한다.

## 결과

- Phase 3까지 브로커가 없다. 오프셋, 수동 커밋, 리밸런스, 소비자 강제 종료·브로커 재시작 훈련은 Phase 4에서 한다.
- 재생 속도 없이 방출하면 5년치 파일이 한꺼번에 생긴다. Phase 1의 신선도 경보 훈련은 원천의 `--speed`(원천 ADR-013)나 방출을 멈췄다 다시 보내는 방법으로 한다.
- Phase 4에서 쓸 Redpanda compose와 토픽 스크립트, 토픽 설계는 git 이력(PR #2, PR #6)에 있다.
