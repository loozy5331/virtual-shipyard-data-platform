# ADR-002 원천 계약 사본

- 상태: 확정
- 날짜: 2026-10-27, 2026-11-10 다시 씀

## 맥락

원천(시뮬레이터)은 이벤트 봉투와 payload 10종, 재발행 요청의 형식을 `schemas/`에 JSON Schema로 둔다. 원천이 고치면 이 파일들이 바뀐다. 플랫폼이 원천 레포를 그때그때 따라가면, 원천이 무엇을 바꿨는지 모르는 채 파이프라인의 동작이 바뀐다.

## 결정

1. **태그로 고정한 사본을 쓴다**
   - 원천 태그 하나의 `schemas/`(봉투, payload 10종, 예시, 재발행 요청)를 `contracts/`에 그대로 복사한다.
   - `contracts/VERSION`에 태그, 커밋, 다시 복사하는 명령을 적는다.
2. **사본은 손으로 고치지 않는다**: CI가 `VERSION`의 커밋에서 원천 `schemas/`를 받아 `contracts/`와 비교하고, 다르면 실패한다. 원천이 새 태그를 내면 다시 복사하고, 깨지는 테스트를 보고 고친다. 바뀐 내용은 diff로 리뷰한다.
3. **사본은 처음 쓰는 할 일과 함께 들인다**
   - bronze는 줄을 그대로 담기만 해서 사본이 필요 없다(schema on read의 저장 쪽).
   - silver가 봉투를 열로 펴는 Phase 1 `feat/silver`에서 사본과 CI 대조를 들인다. 이때 "silver의 열 이름·타입이 계약의 봉투와 맞는가"를 테스트한다. 태그는 그때의 원천 최신을 쓴다(`v0.3.0`~`v0.5.0`의 스키마는 같다).
   - 실제로 온 줄을 사본으로 검증하고, 어긴 줄과 모르는 `event_type`을 격리 표로 보내는 일은 Phase 3 `feat/contract`에서 한다. 그때까지 silver는 모르는 형식의 줄에서 실패한다.
   - 재발행 요청 형식은 Phase 2에서 쓴다.
4. **스키마 레지스트리는 쓰지 않는다**: 레지스트리가 메시지를 지키려면 프로듀서(원천)가 등록한 스키마의 ID를 붙여 보내야 한다. 그런데 원천은 봉투 JSON을 그대로 보낸다(원천 ADR-007). 플랫폼만 쓰면 사본을 하나 더 두는 것과 같다.

## 결과

- 원천이 계약을 바꿔도 플랫폼은 사본을 다시 복사하기 전까지 영향을 받지 않는다. 대신 다시 복사하기를 잊으면 새 이벤트 종류가 격리 표에 쌓인다. Phase 3부터는 격리 표 행 수를 감시한다.
- 봉투는 원천이 고정했고, 이후에는 `event_type`과 payload 필드를 더하기만 한다(원천 봉투 계약). 그래서 사본을 다시 복사해도 기존 열은 깨지지 않는다고 기대할 수 있다.
