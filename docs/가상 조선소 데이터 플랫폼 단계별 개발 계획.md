# 가상 조선소 데이터 플랫폼 단계별 개발 계획

2026-10-27 기준 · 원본(편집용): https://claude.ai/artifact/DvWWpHW7oCEF26bfxkKobW · 원천: [virtual-shipyard-simulator](https://github.com/loozy5331/virtual-shipyard-simulator) `v0.3.0`([원천 계획](https://github.com/loozy5331/virtual-shipyard-simulator/blob/develop/docs/가상%20조선소%20시뮬레이터%20단계별%20개발%20계획.md))

가상 조선소 시뮬레이터가 내는 노이즈 섞인 이벤트를 받아, 정답과 똑같이 복원한 silver와 OEE·리드타임 마트를 만든다. 처음부터 docker compose 위에서 Kafka(Redpanda) 토픽으로 받고, 같은 토픽을 배치와 스트림이 서로 다른 소비자 그룹으로 나눠 받는다. 11/22에 Kafka에서 gold까지 정답과 맞춰 공개하고, 12/6에 스트림을 더하고, 12/20에 끝낸다.

**진행 상황**: 계획 수립(10/27). 시뮬레이터가 계획보다 일찍 끝나(`v0.3.0`) 플랫폼을 거제에 있는 동안(Phase 0)에 시작한다.

## 구조: 입구 하나, 배치와 스트림 둘

입구는 처음부터 Kafka 하나다. 배치(0~6단계)가 정답과 같은 기록을 먼저 만들고, 스트림(7~8단계)은 같은 토픽을 다른 소비자 그룹으로 받아 지금 상태를 맡는다. 모두 docker compose 하나로 뜬다.

```
시뮬레이터(원천) ── emitter --sink kafka ──▶ Redpanda (플랫폼 소유)  <source>.events · <source>.manifest, 키 entity_key
        ▲                                         │                         │
        │ 재발행(Kafka)                            │ group: bronze-ingest     │ group: stream-views
        │                                         ▼                         ▼
  requests/*.jsonl ◀── 대사 ◀── silver(dbt-duckdb) ◀── bronze Parquet        워터마크 10분 · 창 안 중복 제거
                        │                                                   실시간 뷰(설비 상태·오늘 가용률, WIP, 도착 지연)
                        ▼
                      gold(OEE · 계획 대비 실적 · QCD · 리드타임 · 보정용 생산성) ──▶ 블록 스케줄러(루프 닫기)
  └── 배치: 수집 컨테이너 + Airflow 3 일 단위 DAG ──┘                         └── 스트림: 상시 컨테이너 ──┘
```

| | 배치 파이프라인 | 스트림 파이프라인 |
| --- | --- | --- |
| 맡는 것 | 정답과 같은 기록과 마트(gold) | 지금 상태를 수 초 안에 |
| 입구 | 소비자 그룹 `bronze-ingest` → bronze Parquet. 파일 이름 = 토픽·파티션·시작 오프셋, 파일을 쓴 뒤 커밋 | 소비자 그룹 `stream-views`. 처리 뒤 커밋 |
| 실행 | 수집은 상시 컨테이너, 변환·대사는 Airflow 3 일 단위 DAG | 상시 실행 컨테이너 |
| 시간 기준 | 도착 날짜(메시지 시각 = `emitted_at`)로 수집, `occurred_at`으로 집계 | 이벤트 시각 `occurred_at`, 허용 지연 10분(가정) 워터마크 |
| 중복 | `event_id` 전체로 제거 | 워터마크 창 안의 `event_id`만 |
| 늦음·누락 | 72시간 증분 병합, 대사·재발행으로 복구 | 워터마크 밖 늦음은 세기만 하고 버린다. 복구는 배치가 한다 |
| 저장 | bronze Parquet(수집만 씀) → `warehouse.duckdb`(Airflow만 씀) | 소비자 상태 `stream.duckdb`(소비자만 씀), 1분마다 뷰 스냅샷 Parquet |
| 산출물 | gold 마트 | 설비 현재 상태·오늘 가용률, 진행 중 블록 수(WIP), 도착 지연 분포 |
| 장애 복구 | 커밋한 오프셋부터 다시 읽기, 같은 오프셋은 같은 파일에 덮어쓰기, `dt` 재실행·백필 | 커밋한 오프셋부터 다시 읽기, 상태는 토픽 보존 기간 안에서 다시 만듦 |

- 둘이 같이 쓰는 것은 토픽과 계약 스키마(`contracts/`)뿐이다. 서로의 저장소에 쓰지 않고, 8단계의 비교 DAG만 스트림 스냅샷을 읽기 전용으로 읽는다.
- DuckDB 파일마다 쓰는 쪽은 하나다. 수집은 Parquet만 쓰고, `warehouse.duckdb`는 Airflow(pool 1, `max_active_runs=1`)만 쓴다.
- 토픽은 원천 계약대로 `<source>.events`와 `<source>.manifest`, 키는 `entity_key`다. 브로커, 파티션 수, 보존 기간은 플랫폼이 정한다.
- docker compose에 Redpanda·Console, Airflow 3(LocalExecutor, Postgres 메타 DB), 소비자를 둔다. 원천은 처음에는 호스트의 `emitter --sink kafka`로 보내고, 시뮬레이터 이미지가 나오면 `source` 프로필로 같이 띄운다.
- 재발행 요청은 플랫폼이 공유 디렉터리 `runtime/requests/`에 쓰고 원천의 재발행 서비스가 토픽으로 다시 보낸다. 플랫폼은 원천 코드를 실행하지 않는다.
- 채점용으로 원천의 정답 로그(`out/truth`)를 읽기 전용으로 마운트한다. 파이프라인은 쓰지 않고 점수판만 읽는다.

## 원칙

- **정답으로 채점한다**: 1단계부터 점수판이 원천의 정답 로그(`out/truth`)와 결과를 맞춘다. 단계의 완료 기준은 점수판의 칸이다.
- **같은 입력이면 같은 결과**: 같은 오프셋은 같은 bronze 파일로, 같은 `event_id`는 한 줄로. 재실행·백필·소비자 재시작이 결과를 바꾸지 않는다.
- **단계마다 끝까지 돈다**: `docker compose up`과 명령 하나로 토픽부터 그 단계의 표와 점수판까지 나온다.
- **처음부터 실제 모양으로, 구성은 간단하게**: 입구는 0단계부터 Kafka, 실행은 docker compose다. 처리는 노트북 한 대에서 도는 DuckDB·Parquet·dbt로 하고 Spark는 쓰지 않는다.
- **경계를 지킨다**: 토픽부터 플랫폼이고, 브로커와 대사도 플랫폼의 것이다(원천 ADR-007·008). 원천에는 재발행 요청 파일로만 말하고, 원천의 내부 일은 원천 계획에 둔다.
- **스트림과 배치를 섞지 않는다**: 소비자 그룹·저장소·실행 주체를 따로 둔다. 정답과 같아야 하는 것은 배치가, 지금 상태는 스트림이 맡는다.
- **단계의 끝에는 세 가지를 남긴다**: 먼저 실패하는 테스트, 결정을 담은 ADR, 회고 한 줄(무엇이 틀렸고 어떻게 알았나). 세 가지가 그대로 면접 원고가 된다.
- **시간**: 거제(11/8까지) 하루 2시간, 서울(11/9부터) 오전 4시간. 단계 하나 = PR 1~2개, 끝나면 README "만든 것"에 한 줄.
- **밀리면 줄이는 순서**: 7단계 스트림 뷰를 설비 상태 하나로 → 9단계 리드타임 마트를 10단계 뒤로. 2단계 수집 신뢰성, 4단계 대사, 6단계 공개, 10단계 루프 닫기는 줄이지 않는다.

## 성장 순서: 왜 이 순서인가

주니어 데이터 엔지니어는 틀린 숫자를 직접 보고, 왜 틀렸는지 찾고, 고친 것을 숫자로 확인할 때 가장 빨리 는다. 그래서 첫 주에 끝까지 관통하는 얇은 파이프라인과 점수판을 만들고, 이후 단계는 점수판의 틀린 칸을 하나씩 고친다.

1. **얇게 끝까지 먼저(1단계)**: Kafka → bronze → gold 지표 하나(설비 가용률)와 점수판. 처음 숫자가 틀리는 것이 정상이고, 무엇을 고쳐야 하는지 점수판이 보여 준다.
2. **정확성 → 신뢰성 → 운영 → 확장 → 성능**: 틀린 데이터를 빨리 만드는 것은 의미가 없다. 성능 측정은 마지막이다.
3. **문제를 먼저 겪고 고친다**: 자동 커밋 소비자로 시작해 강제 종료로 유실을 직접 만든 뒤 수동 커밋으로 고친다. 단계마다 장애 훈련 하나를 완료 기준에 넣는다.
4. **계약은 일찍, 경계는 끝까지**: 스키마 검증과 격리는 3단계에 둔다. 원천과는 계약과 요청 파일로만 말한다.
5. **운영은 마트보다 먼저(5단계)**: 소비 지연·신선도 감시와 백필을 마트를 늘리기 전에 익힌다. 마트가 늘어도 운영 습관이 먼저 잡혀 있다.
6. **배치로 정답 기준을 세운 뒤 스트림(7단계)**: 스트림의 근사 오차는 맞는 배치가 있어야 잴 수 있다.
7. **가치로 끝낸다(10단계)**: 마지막은 루프 닫기다. 데이터가 일정 결정을 바꾸는지를 숫자로 보인다.

점수판의 칸과, 그 칸을 고치는 단계는 이렇다. 숫자는 원천 5년 실행(시드 0)의 노이즈 실측이다.

| 칸 | 보는 것 | 1단계에서 보일 것 | 고치는 단계 | 목표 |
| --- | --- | --- | --- | --- |
| 완전성 | 정답 대비 빠진 이벤트 | 원천 누락 266개 + 소비자 장애 유실 | 2(유실), 4(누락) | 0 |
| 유일성 | 같은 `event_id`가 두 줄 이상 | 원천 중복 559개 + 재전송 | 3 | 0 |
| 늦음 반영 | 늦게 온 이벤트가 제 날짜 집계에 들었나 | 10분 넘게 늦은 1,715개 일부가 빠짐 | 3 | 모두 반영 |

마트 정의는 이렇게 잡는다. OEE의 가용률은 eam의 down→up 구간, 성능은 계획 소요(`planned_end` − 착수) ÷ 실제 소요다. 품질은 불량 이벤트가 아직 없어 1로 둔다. QCD는 D = 계약 납기 대비 인도일, C = 호선별 공수(MH)이고, Q는 보류다. 4M 스윕과 규모 실험은 12/20 뒤 선택 과제로 둔다.

## 이웃 레포

플랫폼은 원천 계약(시뮬레이터 `v0.3.0`의 봉투, `seq`, 마감 집계, 재발행 요청 형식)에만 기댄다. 원천 쪽 할 일은 [시뮬레이터 계획](https://github.com/loozy5331/virtual-shipyard-simulator/blob/develop/docs/가상%20조선소%20시뮬레이터%20단계별%20개발%20계획.md)에 두고, 여기에는 언제까지 필요한지만 적는다.

| 플랫폼이 쓰는 것 | 레포 | 필요한 때 | 상대 계획 |
| --- | --- | --- | --- |
| 이벤트 계약, Kafka 출력(`--sink kafka`, 체크포인트), 정답 로그 | 시뮬레이터 | 0·1단계부터 | 완료(`v0.3.0`) |
| 컨테이너 이미지와 재발행 요청 디렉터리 | 시뮬레이터 | 4단계(11/13) | 시뮬레이터 10단계 |
| 재발행을 Kafka로 | 시뮬레이터 | 4단계(11/13) | 시뮬레이터 11단계 |
| 실제 시간에 맞춘 재생 속도 | 시뮬레이터 | 5단계 감시(11/17), 7단계(11/23) | 시뮬레이터 12단계 |
| 블록 입력 양식과 지연 판정 | `shipbuilding-block-scheduler` | 10단계(12/7) | 플랫폼 10단계 첫 할 일로 확인 |
| 용접 불량 이벤트(QCD의 Q) | 시뮬레이터 | 선택 | 시뮬레이터 9단계 |

원천 쪽이 늦으면 4단계는 호스트에서 `emitter.replay`로 나온 파일을 임시 업로더로 토픽에 넣는다(ADR-005에 임시라고 적음). 7단계는 한꺼번에 보낸 토픽으로 뷰 로직만 확인한다.

## 결정 기록과 열린 질문

| ADR | 정할 것 | 단계 |
| --- | --- | --- |
| 001 스택 | docker compose, Redpanda, Airflow 3(LocalExecutor), DuckDB + Parquet + dbt-duckdb. Spark를 쓰지 않는 까닭 | 0 |
| 002 원천 계약과 토픽 | 토픽·키·파티션 수·보존 기간, 스키마 버전 고정 | 0 |
| 003 전달 보장과 오프셋 | 파일을 쓴 뒤 커밋, 오프셋 이름 파일로 멱등, exactly-once 대신 at-least-once + 중복 제거를 고른 까닭 | 2 |
| 004 계층과 늦게 도착한 데이터 | bronze는 도착 기준, silver는 이벤트 시각 기준, 72시간 되돌아보기, 격리 표 | 3 |
| 005 대사와 재발행 요청 | 대사 범위(마감 집계 30일), 기다리는 시간, 요청 디렉터리 | 4 |
| 006 운영과 백필 | 감시 지표와 경보 기준, 백필은 bronze에서 silver·gold를 다시 만드는 일로 한정 | 5 |
| 007 스트림과 배치 나누기 | 소비자 그룹·저장소·실행 주체 분리, 스트림 워터마크 10분, 복구는 배치만 | 7 |

열린 질문
- Airflow 3 공식 compose와 Redpanda를 노트북 한 대에서 함께 돌릴 수 있는가? 0단계에서 메모리를 재고, 모자라면 Airflow를 standalone 컨테이너 하나로 줄인다.
- 재생 속도 없이 보내면 5년치가 몇 초 만에 들어온다. 배치는 상관없지만, 소비 지연 경보와 스트림 뷰는 재생 속도(시뮬레이터 12단계)가 있어야 의미가 있다.
- 스트림 워터마크 10분은 가정이다. 보통 지연은 p95 39초지만 늦음 3%는 수 시간이라, 워터마크 밖으로 약 3%가 빠질 것으로 본다. 8단계에서 재보고 정한다.
- 호선 금액과 비용 이벤트가 없어 QCD의 C는 공수(MH)로만 본다. 금액이 필요하면 시뮬레이터 계획에 요청으로 올린다.
